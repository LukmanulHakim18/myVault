01 · Overview

Dua platform, satu backend

Web Reservasi dan Rent Revamp berbagi backend MRG yang sama — termasuk sistem ID, order orchestrator, dan payment flow. Yang membedakan hanyalah channel & produk.

Web · via ocelot

Web Reservasi

Booking via web (lewat gateway ocelot), tanpa login. Fokus Goldenbird: Airport Transfer, Hourly, Daily. Pembayaran via Nicepay payment link.

MyBB · via MRG API GW

Rent Revamp — MyBB

Rental via aplikasi MyBB (dengan login) yang nge-hit MRG API Gateway. BB & SB (hourly), GB (hourly & daily). Immediate hanya untuk SB & BB.

Keduanya berbagi backend, tabel order, & Two-Level ID yang sama di orderorchestrator — yang berbeda: gateway, katalog produk, mode order, pembayaran, & siapa yang push HO.

04 · Model Booking & Order

Two-Level ID Generation

Satu Booking membungkus satu atau lebih Order. Struktur ID di-expose langsung ke customer & support sehingga mudah ditelusuri.

Web · Goldenbird ATF
WBG-NQBMEK7P2QF01 · booking ↳ WBGA-NQBMEK7P2QF02 · order
Rent · Goldenbird Daily
MYG-NQBMEK7P2QF05 · booking ↳ MYGL-NQBMEK7P2QF06 · order
Prinsip kunci: ID di-generate hanya setelah operasi sukses (mis. charge berhasil) — no ID waste, tidak ada gap di sequence, tidak ada dangling order.

06 · Order Flow

Perjalanan satu order

1Pilih fleet — Gateway request fleet list → service-info, sesi dimulai di session-manager.
2Create order — create order → orderorchestrator; get chosen fleet dari session.
3Pay order — pay order → payment-processor → BB Payment → UPG.
4Events — booking / payment / order-event menyebar ke orderquery, notificationcenter (Web → email · App → push via Firebase/FCM) & legacy stream.
5Push HO — BB Price push data ke HO; partner update status balik via webhook forwarder.
State transisi yang dilaporkan orchestrator: transaction created → payment completed → transaction completed.
07 · Payment

Reserved Budget ECV ✓ Deployed

Charge dipindah ke depan (pre-order) untuk membunuh masalah order gantung.

Masalah

Order gantung

Charging dilakukan belakang → user saldo kurang tetap bisa buat banyak advance order, lolos validasi, lalu gantung saat charging aktual. Data booking & payment jadi inkonsisten.

Solusi

Pre-order charge

validate policy → validate balance → charge → reserve → create order. Order (dan ID-nya) baru dibuat setelah charge sukses.

Scope: fixed-tariff only (hourly/daily) — bisa dihitung di awal. Argo/distance-based tidak termasuk karena nominal belum pasti sampai trip selesai. Refund wajib idempotent.
08 · Payment

Push HO — ECV vs Non-ECV Draft

Non-ECV

push_ho segera

Setelah payment callback masuk (Nicepay → UPG → MRG), MRG langsung request Push HO ke BB Payment. Selesai.

vs

ECV

tunggu order complete

MRG menunggu status order = COMPLETE dulu, baru Push HO — supaya budget akurat termasuk overtime, extra, tipping. Mengikuti pola Cititrans.

Siapa yang push HO: UPG untuk SB & BB, sisanya (GB) standard MRG — via flag is_push_ho ("true" → UPG, "false" → MRG).
