Risiko arsitektur yang perlu keputusan

Hal-hal yang muncul justru saat kedua peta disandingkan — kandidat utama untuk dibawa ke forum risk review.

Kritis

Dual payment gateway di UPG

mrg-gateway (microservices) berjalan paralel dengan meta-payment-gateway (monolith, 8 provider inline). Migrasi belum tuntas → logic terduplikasi.

UPG · gateway
Kritis

Data transaksi terfragmentasi

Tiga tempat penyimpanan transaksi berbeda: transaction (SSOT baru), bbecv-adapter/DB bbecv (legacy), dan DB milik MPG. Menyulitkan rekonsiliasi.

UPG · data ownership
Tinggi

Business logic di gateway

Gateway berperan ganda sebagai orchestrator (54 RPC) alih-alih routing-only — coupling tinggi, sulit di-test independen.

UPG · tech-debt #1
Tinggi

PostgreSQL sebagai SPOF

Banyak service berbagi DB; blast-radius luas bila DB down. Perlu konfirmasi status HA/Patroni di kedua ekosistem.

MRG + UPG · infra
Tinggi

JWT tak bisa di-invalidate

Stateless JWT MRG belum punya mekanisme logout/blacklist — risiko bila kebijakan logout diaktifkan atau akun dikompromikan.

MRG · tech-debt
Terkendali

Resilience pattern matang

Circuit breaker, idempotency key, distributed lock, dan retry cron (upg-scheduler) sudah jadi standar di UPG.

UPG · positif
Aturan main

Rules Catalog

Aturan dipisah dari diagram supaya bisa di-maintain sendiri. Tiga kategori, semua diturunkan dari pola nyata di kedua ekosistem — bukan teori.

G1

Satu entitas, satu pemilik data

Setiap entitas punya satu service pemilik. Service lain mengakses lewat pemiliknya (gRPC), tidak pernah menyentuh DB-nya langsung. Transaksi = transaction; akses data legacy = lewat bbecv-adapter.

Kenapa: saat ini ada 3 tempat transaksi berbeda. Aturan ini menghentikan fragmentasi bertambah dan mengarahkan konsolidasi.
G2

Gateway adalah batas, bukan tempat business logic

Gateway hanya routing, auth, dan komposisi. Business logic milik domain service. Orkestrasi yang kompleks boleh, tapi keputusan bisnis turun ke service yang bertanggung jawab.

Kenapa: business logic di API Gateway (UPG tech-debt #1) bikin coupling tinggi dan rawan regression.
G3

Integrasi eksternal lewat forwarder khusus

Core domain tidak memanggil sistem eksternal langsung. Selalu lewat gateway/forwarder berdedikasi: upgforwarder, taxipartnergateway, webhook-fwd.

Kenapa: mengisolasi perubahan API pihak ketiga dan tempat menaruh circuit breaker.
G4

Posting ke keuangan (SAP/HO) selalu via event

Semua posting ke SAP/HO lewat intermediate-ho secara event-driven dan idempotent — bukan panggilan sinkron langsung dari flow utama.

Kenapa: SAP lambat & kadang gagal; event + idempotency mencegah double-post dan tidak memblok transaksi user.
T1

Pilih protokol sesuai sifat panggilan

gRPC untuk sinkron internal · REST untuk client-facing & integrasi legacy · PubSub untuk async/event & fan-out.

Kenapa: sudah jadi pola de-facto di kedua ekosistem; menstandarkannya menghapus debat per-fitur.
T2

Resilience wajib untuk setiap dependency

Circuit breaker (gobreaker) untuk semua call lintas-service & eksternal. Distributed lock (Redis) untuk operasi non-idempotent seperti charge.

Kenapa: mencegah cascade failure & double-charge — sudah terbukti di mrg-gateway cross-charge.
T3

Setiap event consumer harus idempotent

Konsumer PubSub memakai natural/idempotency key (mis. transaction_id + status + type) supaya redelivery tidak menggandakan efek.

Kenapa: PubSub menjamin at-least-once; tanpa idempotency, redeliver = double-post.
T4

Rollout lewat feature flag, bukan hardcode

Perubahan berisiko diaktifkan bertahap via Flipt (granular per BIN/user/persentase), bisa di-rollback tanpa deploy ulang.

Kenapa: dipakai routing-service & BB Prime; jadikan standar lintas-tim.
T5

Observability & log aman secara default

Elastic APM di semua service; field sensitif (password, token, PII) di-mask di log. Logger distandarkan formatnya.

Kenapa: UPG sudah konsisten; MRG masih punya tech-debt standardisasi logger (#5) yang perlu ditutup.
D1

Bikin service baru, atau extend yang ada?

Domain/provider baru dengan lifecycle & data sendiri → service baru (pola {provider}-service). Fitur yang me-reuse domain existing → extend.

Contoh: BB Prime tidak bikin service baru — ia reuse TOP/FDS/pricing. Provider e-wallet baru = service baru.
D2

Sinkron (gRPC) atau async (PubSub)?

Butuh hasil untuk melanjutkan flow → gRPC. Fire-and-forget, posting HO, atau notifikasi lintas-service → PubSub.

Aturan praktis: kalau user menunggu hasilnya, sinkron; kalau tidak, jangan blok — pakai event.
D3

Butuh data domain lain?

Selalu lewat service pemiliknya via gRPC. Jangan query DB domain lain, dan jangan duplikasi datanya kecuali sebagai cache yang jelas TTL-nya.

Kenapa: akses DB lintas-domain adalah akar fragmentasi data yang sekarang jadi risiko kritis.
D4

Di mana menaruh retry?

Gagal transient di flow utama → circuit breaker + retry terbatas. Butuh penyelesaian eventual (mis. charge gagal) → upg-scheduler / retry queue.

Kenapa: memisahkan retry cepat (in-flow) dari retry lambat (background) menjaga latency user tetap rendah.
Catatan

Open items & langkah berikut

Scope = Fase 1

Peta ini MyBB/MRG + UPG. BBG penuh jauh lebih luas (bb-dispatch, e-billing, e-timesheet, outlet, IoT, dll.) — perlu konfirmasi VP apakah Fase 2 melingkupi itu.

Port provider perlu konfirmasi

Beberapa provider UPG (DANA / LinkAja / ShopeePay) tampak berbagi port 9113 di config gateway — verifikasi ke tim UPG sebelum final.

BB Prime belum di peta MRG

BB Prime adalah fitur (bukan service baru), tapi memunculkan integrasi BBD granular & Flipt yang belum tercermin di landscape MRG.

Bawa risiko ke risk review

Enam risiko di atas adalah kandidat untuk sesi risk assessment lintas tim (MRG + UPG + BBD) yang sudah ada di backlog.
